# 电信经营证据分析v06（telecom-decision-evidence-v06）

## 何时使用
- 用户就当前脱敏电信演示场景提问：这轮是否需要调人、结果卡在哪一环、订单或工单该给谁、某人的积分如何形成、执行后如何回看。
- 用户补充人员/任务/结果/积分事实，或提出"如果某人不可用"的 What-if，或采纳/调整/驳回上一轮建议。

## 何时不要使用
- 本轮没有提供当前有效场景 JSON（不得凭空生成事实）。
- 要求真的调人、派单、改绩效或发布规则（本技能只出待确认建议）。
- 要求跨岗位按原始积分排名。
- 与电信经营决策无关的通用问答。
- 反例："帮我按积分从高到低排全网格的人"→ 不触发，应拒绝；"直接把人调过去并改他的绩效"→ 不触发，应拒绝写动作。

## 前置条件
- 当前脱敏场景 JSON 与 DecisionResponse Schema 可读。
- 个人库"电信经营演示规则v06"已入库文档 TELECOM-DEMO-RULES-V06。

## 执行步骤
1. 先取证据：kb_search 在个人库"电信经营演示规则v06"检索，命中 TELECOM-DEMO-RULES-V06 后 kb_read 读取分块并逐条引用，写法 `TELECOM-DEMO-RULES-V06#chunk N`。只允许 kb_search/kb_read，禁止扫描知识库存储目录；禁止用固定标准答案或固定 HTML 冒充模型输出。
2. 规则未入库或未命中：直接进 blocked，写明"规则库无命中"，不虚构规则。RAG 只解释规则，不覆盖当前场景 JSON 中的事实（RULE-06）。
3. 读当前场景 JSON 与 Schema，登记本轮可用事实（人员、岗位、任务、订单/工单、结果、积分事件、负荷、时限、保障底线）及其失效/撤回状态。
4. 证据门（RULE-02）：人员、任务、结果或积分事实不足 → 输出 blocked，不点名、不输出到人行动；被撤回或失效的历史人员明细不得复用；无负荷、技能、时限、保障底线证据不得宣称人员够用。
5. 意图匹配与决策顺序（RULE-03）：先同岗同口径的量、结果与质量 → 再看任务产品结构、人员匹配、有效订单或一次竣工、积分正负项与账期调整 → 最后容量与保障底线；先网格内调整，仅存在明确缺口才评估区县跨网格支援。根因必须对应可执行动作，不得由平均积分反推个人。
6. 岗位分账（RULE-01）：营销用贡献积分，装维用履约积分，禁止跨岗位原始积分排名；积分解释回到个人业务事件、当前负荷与质量证据。
7. 分支与约束（RULE-04/RULE-05）：What-if 建独立分支，不覆盖基础事实；"某人不可用"是约束变更，修订候选排除该人员，且该约束在后续追问中继续保留、不恢复旧安排；缺可用工时标注"待确认"。AI 仅提建议，采纳/调整/驳回只形成待负责人确认的候选状态。
8. 回看：T 看执行、有效订单、一次竣工；T+1 看积分兑现、质量、早期保有；T+2 看撤单、离网、最终在网。

## 输出契约（DecisionResponse）
- 只输出符合 Schema 的 JSON，无代码围栏、无前后解释；organization_scope 保留省/市/区县/网格，默认 analysis_level=grid。
- full：证据充分，给出完整判断；delta：事实或约束变更，仅给受影响的增删改与理由；blocked：证据不足或数据失效，只列已知事实、缺失信息与下一安全动作，不点名、不到人。
- 结论顺序：经营判断 → 一根针（根因）→ 到人行动 → 验证与反馈；主回答用管理语言，不出现模型、算法等工程术语。

## 失败语义
规则未入库 / 检索无命中 / 场景缺失 / 证据不足 → blocked 并说明缺什么；事实冲突以当前有效场景 JSON 为准并标注冲突，不覆盖事实；本技能不执行任何写动作。

## 外部依赖
知识库检索（kb_search / kb_read）与个人库"电信经营演示规则v06"；当前脱敏场景 JSON；DecisionResponse Schema。无网络与凭证需求。
