# 网格经营分析方法（可复用版）

- 版本：v1.0 / 2026-10-26
- 适用：脱敏演示场景下的"网格人力—任务匹配"分析（TELECOM-DEMO-A-BRANCH 系列）
- 规则依据：TELECOM-DEMO-RULES-V06（v0.6），经知识库读取；该文档声明仅适用脱敏演示案例，**不是正式运营商制度**
- 方法来源：本项目初稿 `01_网格经营分析.md` 被纠正的过程，纠正记录见 `evidence/2026-10-26/01_网格经营分析_修订版.md`
- 使用边界：本方法只产出"待人工确认的建议"，不执行调人、派单、改绩效

## 0. 一句话流程

**核对口径 → 核量/结果/质量 → 核结构匹配 → 核容量与保障底线 → 标证据等级 → 合成待确认建议**

五条方法名（本文的可复用骨架）：

| 编号 | 方法 | 解决什么问题 |
| --- | --- | --- |
| M1 | 先核对指标口径，再检查容量与任务匹配 | 指标被当成结论用 |
| M2 | 缺证时说"待核实"，不说"够用"也不说"该增员" | 把"否定一个主张"升级成"肯定其反面" |
| M3 | 缺少个人证据不点名 | 用网格级平均去安排具体的人 |
| M4 | 假设不覆盖原事实 | 推理悄悄替代了场景数据 |
| M5 | 建议需人工确认 | AI 输出被当成已执行动作 |

## M1 先核对指标口径，再检查容量与任务匹配

**何时用**：任何时候你手上有一批指数名（业务量指数、贡献积分、一次竣工率、质量指数、业务结果完成率）并想据此谈人力。

**怎么做（口径四问，任一问无答案，该指标只能描述现状、不能用于人力推断）**

1. **分子分母**：这个指数是数量、工时、金额还是笔数？分母是基准值、目标值还是上期值？
2. **人均还是总量**：网格级总量下降 12%，人均是升是降？人数变化是否已经进过分母？
3. **同口径**：两个被比较的数是否同岗位、同账期、同考核口径（装维履约积分 vs 营销贡献积分不可互比）？
4. **质量联动**：这个量指标是否已被质量问题污染（例：一次竣工率 31% 时，同样任务量需要更多工时，指数不变但工作量变了）？

**判定门槛**
- 口径齐 → 可进入 M2 的容量核验；
- 口径缺任一问 → 结论止步于"该指标显示 X 偏低"，**不得**出现"不需要增人/人员够用"。

**反例（本项目初稿踩过）**：装维业务量指数 88%（低于基准）被直接读成"人多也不会多出任务 ⇒ 不缺人"。错误在于该指数不含可用工时与任务复杂度；同样 88% 的任务量，若单任务复杂度上升或一次竣工率仅 31%，所需工时可能反而高于基准 100% 时的水平。**指数是量的口径，工时结论必须另取工时证据。**

**产出位置**：分析文档的"输入事实"节，逐条标注口径来源字段；口径未定义项进入"待补充证据"。

## M2 缺证时说"待核实"，不说"够用"也不说"该增员"

**何时用**：被问"到底缺不缺人"这类二选一问题时。

**怎么做（三档结论，按证据选，不许越级）**

| 档位 | 表述 | 需要的证据 |
| --- | --- | --- |
| A 可判定 | 容量能/不能覆盖任务 | 可用工时 + 工时标准 + 保障底线 |
| B 待核实 | **当前证据不支持直接增员，先核实容量和匹配** | 双方均缺证即可成立 |
| C 不合格 | "不缺人/人员够用""该增员" | 单选题式断言，通常无证据 |

**关键动作：把"否定证据"和"肯定反面"分开。**
- "没有证据支持增员" ≠ "有证据证明人员够用"。
- 同理，"匹配假设有场景支持" ≠ "已排除人员不足"。

**反例**：初稿用"31% vs 88% 差 57 点，人手补 10~20% 解释不了"来支持匹配假设。这是拿结果指数差去除一个不存在的人手—产出弹性系数，量纲不成立。**指数差（百分点）与人数（百分比）不同量纲，不能相互比较，除非有实测弹性系数。**

**产出位置**：结论句只用 B 档表述；A 档必须附证据编号。

## M3 缺少个人证据不点名

**何时用**：想把任务、机会或人员往具体某个人身上安排时。

**怎么做**

1. 先判证据粒度：网格级聚合 vs 个人级业务事件（工单、订单、积分明细、质量扣减）。
2. 只有聚合数据 → 结论**止步于网格级**：可以说"某类任务与承接人技能不匹配"，不可以说"张三不适合做复杂任务"。
3. 缺个人证据但仍被要求给方案 → 返回 `blocked`：`root_causes` / `people` / `actions` 留空，把网格级事实放进 `evidence_drawer`。
4. 需要"到人"时，先补：个人业务事件 + 当前负荷 + 质量证据（三者缺一不可）。

**反例**：10 人中仅 2 人有事件明细，初稿仍给出 10 条到人安排。虽然每条都标了 `pending_confirmation`，但**证据资格不足时，标注确认状态并不能让它合法**——正确做法是整批不出、只报缺口。

**产出位置**：DecisionResponse 的 `response_mode`；分析文档"待补充证据"中的个人级条目。

## M4 假设不覆盖原事实

**何时用**：写任何分析文档，尤其是要给别人复核的。

**怎么做：物理分节，不许混写**

| 节 | 内容 | 标注要求 |
| --- | --- | --- |
| 输入事实 | 场景 JSON 里的数字、人员、指数 | 标字段路径与 fixture id |
| 材料已有参考判断 | fixture/规则库自带的根因、capacity_check 等 | 标"**场景证据**，非独立核验" |
| 本轮推理 | 你的假设、因果链、优先级 | 标"**未验证假设**"，并写反证条件 |
| 待补充证据 | 补齐哪一项就能升级结论 | 编号 + 用途 + 优先级理由 |

**铁律：假设与事实冲突时，改假设，不改事实；事实不足时，写成缺口，不写成默认值。**

**反例**：fixture 的 `capacity_check.status=covered_after_reassignment` 是场景预置结论，初稿拿它当"独立核验通过"去否掉增员。按 RULE-06，场景预置根因与容量结论只能称场景证据，**不得宣称独立因果估计**。

---

## M5 建议需人工确认

**何时用**：任何要落到"谁做什么"的输出。

**怎么做**

1. 每条建议统一 `status = pending_confirmation`，写明：执行人、变更内容、观测窗口（T/T+1/T+2）、回滚条件、需要的授权层级。
2. AI 不自动调人、不派单、不改绩效；采纳/调整/驳回只形成候选状态，由业务负责人决定。
3. 交付时明确写出"本轮未执行任何人员调度或生产变更"。

**反例**：把"10 条到人安排"当成可执行动作输出，即使逻辑正确，也越过了授权边界。

## 6. 五步执行清单（可直接照抄）

- [ ] 1 列出所有要用的指数，逐条过 M1 口径四问，标记"可用/仅描述"
- [ ] 2 按 RULE-03 顺序核：量 → 结果 → 质量（同岗同口径）
- [ ] 3 核结构匹配：任务产品结构 × 承接人技能 × 当前负荷 × 有效订单/一次竣工 × 积分正负项
- [ ] 4 核容量与保障底线：可用工时、工时标准、保障预留
- [ ] 5 按证据粒度决定输出档位（M2/M3），合成 `pending_confirmation` 建议（M5），全文按 M4 分节

## 7. 常见错误对照表

| 错误写法 | 为什么错 | 改成 |
| --- | --- | --- |
| 量指数低于基准 ⇒ 不缺人 | 指标口径不含工时与复杂度 | 该指标显示量偏低；容量待核实 |
| 结果落差 N 点 ⇒ 缺/不缺 X% 人 | 量纲不同，缺弹性系数 | 落差是结果侧现象，原因待分解 |
| 场景 capacity_check 通过 ⇒ 容量已核验 | 场景证据 ≠ 独立核验 | 场景预置结论，仅作参考 |
| 平均积分低 ⇒ 这个人不行 | 聚合数据推个人 | 网格级结论；到人需个人事件 |
| 给到人安排但标"待确认" | 证据资格不足不因标注而合法 | 整批不出，改报缺口 |
