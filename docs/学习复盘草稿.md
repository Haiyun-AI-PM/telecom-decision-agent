# 学习复盘草稿（2026-10-26，安装版 CogSeed 1.4.0）

> 本文件是本轮复盘，只记录这一轮真实发生的事。此前开发版会话的复盘与 8 份历史响应留在 `evidence/response-*.json`，不并入本文件。

**一句话结论**：这轮最大的收获不是"算出了答案"，而是学会在被质疑时先撤掉支撑不住的推断，再补上需要什么证据才能说那句话。

## 一、我在 CogSeed 协助下做的四件事

1. **追问核对**：把"10 人 7:3、结果不理想"这个模糊处境拆成可核对的项——口径、量、结果、质量、结构、容量、证据等级，逐项标"材料说的 / 我推的 / 还没证的"。
2. **纠正一个过快推断**（下节详述）。
3. **验证变更条件**：增员、人员不可用、证据被撤回三种输入下，哪些判断会变、哪些不会变。
4. **复用分析方法**：在新任务（高意向机会量变化、尚无新明细）里实际调用方法文档，而不是重新发明一套。

## 二、被纠正的推理问题：从 88% 直接跳到"不缺人"

- **原来的推断**：装维业务量指数 88%（低于基准），所以任务量不多，所以不缺人。
- **错在哪**：88% 是**任务量与基准的相对关系**，它不含可用工时、技能结构、任务复杂度，也不含保障底线。量的口径不能当工时口径用。同理，初次分析直接比较量果指数落差与增员百分比，也缺少两者之间的因果模型，不能据此判断增员效果。
- **改成了什么**：**"当前证据不支持直接增员，先核实容量与匹配"**。注意这句话不等于"人够用"：没有证据支持 A，不等于有证据支持非 A。
- **同时降级的东西**：fixture 里的 `capacity_check`（7 人可覆盖 6 项复杂任务）只是场景给定证据，不是独立核验结果，不能拿来当中立依据用。
- **还留着的**：原始 10 人基线、五项指数、两条根因描述——事实不因推断被撤回而消失，只是不再被当成结论。

## 三、验证变更条件时学到的事

- **增员假设**：新人工时与技能都未知，就不能派任务，也不能补造数字；原 10 人基线必须原样保留，另开分支写"假设增加 1 人"。
- **营销 C 不可用**：不能把 C 的任务自动全转给营销 A——A 自己只有 4 条明细、负荷未知，转过去是把一个未核实问题挪成另一个未核实问题。先撤回"3 名营销可覆盖机会池"这类容量结论。
- **证据被撤回**：只留聚合数据、直接问"具体该重派谁"时，正确动作是**停止点名**、返回 `blocked`、只报缺口。守不住这一条，前面所有"证据边界"都是口号。

## 四、复用分析方法

新任务里我直接调用了方法文档的五条（口径先行、缺证说待核实、个人证据门不点名、假设不覆盖原事实、建议需人工确认），先问清判定标准/窗口/分母/去重四件事，再谈谁做什么。方法被复用一次、且限制了输出形式，才算真的落地；复现记录见 `evidence/2026-10-26/11_方法复用记录_高意向机会量.md`。

## 五、必须如实写下的过程问题

- **业务 Agent 首轮返回 `blocked`**（不点名、无到人动作）——这是它做对的地方。
- 但**后续一次追问界面显示"未返回终态"，重试也没有可核实的成功结果**。所以本轮三项输入验证、94.34 追问与方法复用，**都是在这个主会话里完成的**，不能记成业务 Agent 的终态产出。
- **本版没有出现"经营决策应用"卡片**，所以"应用已在本机跑起来"这句话本轮不成立。
- **知识库关键词检索没有直接命中规则**：两次 `kb_search` 的召回都被本项目自己的旧分析稿和无关的验收类文档占了；最后是 `kb_list` 定位库内路径、`kb_read` 按路径读取才拿到 RULE-01…06。这是"库内已索引 + 按路径读取"，**不是语义召回命中**，不能写成 RAG 命中了规则。
- **自定义校验不是完整 JSON Schema 验证**：本机没有 `jsonschema` 库，脚本是手写子集实现，只证明"与 Schema 声明约束一致"，不宣称通用兼容。
- **教师尚未评审**，`TEACHER-CHECK.md` 7 轮仍是"未验证"。
- 打包失败（缺 `src/main/util/migrate-source-data-root.cjs`）是**历史**开发版构建状态，本轮未发生、也未修复，不能拿来当本轮结果，也不需要美化掉。
